Entity-Relationship (ER) Model & 3NF Decomposition

Normalized relational database architecture eliminating transitive dependencies (1NF → 2NF → 3NF).

ENTITY: APARTMENTS Parent Table
  • 🔑 flat_numberVARCHAR(10) PK
  • block_wingVARCHAR(20)
  • floor_noINT
  • bhk_typeENUM('2BHK','3BHK')
ENTITY: RESIDENTS Core Table
  • 🔑 resident_idVARCHAR(12) PK
  • 🔗 flat_numberVARCHAR(10) FK
  • full_nameVARCHAR(100) NN
  • resident_typeENUM('Owner','Tenant')
  • phone_numberCHAR(10) UNIQUE
  • email_addressVARCHAR(120)
  • family_membersINT CHECK(>0)
  • move_in_dateDATE NOT NULL
  • statusENUM('Active','Moved Out')
ENTITY: VEHICLES Child (0..N)
  • 🔑 vehicle_numberVARCHAR(15) PK
  • 🔗 resident_idVARCHAR(12) FK
  • vehicle_typeVARCHAR(20)
  • parking_slotVARCHAR(10)
1 : N Relationship (APARTMENTS → RESIDENTS): One apartment flat can house one or multiple registered residents over time.
1 : N Relationship (RESIDENTS → VEHICLES): Each resident may register zero or more personal vehicles linked via Foreign Key resident_id.
3NF Compliance: All non-key attributes depend strictly on the Primary Key (resident_id), avoiding partial or transitive dependencies.

SQL DDL Schema Definition 

CREATE DATABASE IF NOT EXISTS apartment_db;
USE apartment_db;

CREATE TABLE residents (
  resident_id VARCHAR(12) PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL,
  flat_number VARCHAR(10) NOT NULL,
  block_wing ENUM('Block A','Block B','Block C','Block D') NOT NULL,
  resident_type ENUM('Owner','Tenant') NOT NULL,
  phone_number CHAR(10) UNIQUE NOT NULL,
  email_address VARCHAR(120),
  family_members INT NOT NULL CHECK (family_members >= 1),
  vehicle_number VARCHAR(15) DEFAULT NULL,
  move_in_date DATE NOT NULL,
  emergency_contact CHAR(10) NOT NULL,
  status ENUM('Active','Moved Out') DEFAULT 'Active',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
